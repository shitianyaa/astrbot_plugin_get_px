# 贡献说明

## 贡献目标

优先做这些事情：

- 修复发图、签到、下载、过滤和前端页面回归
- 补充测试与最小回归用例
- 让 README、配置 schema 和 docs 保持一致
- 改善排障日志和错误可观测性

不建议直接上来做大而散的重构，除非先把行为边界讲清楚。

## 改动前先理解当前边界

改动前先确认自己触碰的是哪条边界，不在这里复制业务规则：

- 架构和主要流程见 [`../project/architecture.md`](../project/architecture.md)
- 配置字段语义见 [`../project/configuration.md`](../project/configuration.md)
- 插件定位和能力边界见 [`../project/overview.md`](../project/overview.md)
- 签到功能说明见 [`../user/checkin.md`](../user/checkin.md)
- 指令参考见 [`../user/commands.md`](../user/commands.md)

如果准备做的事和这些边界冲突，需要先明确说明为什么。

## 推荐的贡献流程

1. 明确问题或目标
2. 先阅读相关代码与现有文档
3. 小步提交，单次改动尽量围绕一个目的
4. 先补或更新测试，再补文档
5. 通过语法检查和最小回归测试后再提交 PR
6. 记录开发进度到 `Progress/` 目录

## 发布前检查

- `metadata.yaml.version`、`main.py` 的 `PLUGIN_VERSION`、README 徽章和 CHANGELOG 首个版本段必须一致。CHANGELOG 使用 `## vX.Y.Z (YYYY-MM-DD)`，README 更新日志链接指向该版本段；不保留分支临时措辞。
- 运行 `python -m pytest -q tests` 及语法、配置 JSON 检查，确认 PR 质量检查通过后再合并。
- `Release plugin archive` 在 `master` 的 CHANGELOG 最新版本改变时自动创建 tag 和 Release。发布 job 不依赖质量检查，不要将合并视为只更新代码；使用新版本号，并确认同名 tag 不指向其他提交。
- 现有工作流重新发布已有版本会覆盖 Release 附件和说明。不要为修复已发布版本直接重跑发布，优先发布新版本。

## 文档同步要求

文档同步细则统一维护在 [`maintenance.md`](./maintenance.md#文档同步)。贡献文档只强调一点：不要只改代码而让 README、docs、CHANGELOG 失真。

## 代码风格

通用工程原则见 [`engineering-principles.md`](./engineering-principles.md)。贡献时优先沿用现有模式，不要为了局部问题顺手大改 unrelated 模块。

## PR 描述建议

新代码和修复改动的 PR 目标分支应根据项目约定确定。

建议至少写清楚：

- 背景问题
- 改动范围
- 风险点
- 验证方式

## 提交规范

### 提交信息

- 第一行简明扼要描述改动（50 字以内）
- 空一行后详细说明改动原因和影响
- 引用相关 issue 或讨论链接

示例：

```
修复图片下载器返回值类型不匹配

ImageDownloader.download() 改为返回 (path, size) 元组，
但部分调用方未更新解包逻辑，导致运行时错误。

本次修复：
- 更新 pixiv/search.py 中的调用
- 更新 plugin_api/api.py 中的调用
- 修复测试 mock 对象返回值
- 添加回归测试

修复 #123
```

## 改动范围建议

### 小改动（推荐）

- 修复单个 bug
- 添加单个功能
- 更新单个配置项
- 补充单个测试

### 中等改动

- 重构单个模块
- 添加多个相关功能
- 更新多个相关配置项
- 迁移数据库 schema

### 大改动（需要讨论）

- 重构多个模块
- 改变核心架构
- 修改数据存储方式
- 大规模依赖升级

## 常见贡献场景

### 修复 bug

1. 复现 bug 并记录复现步骤
2. 定位根本原因
3. 修复问题
4. 添加回归测试防止再次出现
5. 更新相关文档（如有必要）
6. 提交 PR 并附上复现步骤和修复说明

### 添加功能

1. 确认功能是否符合插件定位
2. 设计功能接口和数据结构
3. 实现功能
4. 添加测试覆盖
5. 更新用户文档和配置文档
6. 提交 PR 并说明功能用途和使用方式

### 更新配置

1. 修改 `_conf_schema.json`
2. 更新代码中的配置读取逻辑
3. 同步更新 `README.md` 和 `docs/project/configuration.md`
4. 考虑向后兼容性
5. 添加或更新相关测试
6. 提交 PR 并说明配置变更原因

### 重构代码

1. 说明重构的动机和目标
2. 确保重构不改变外部行为
3. 保持测试通过
4. 小步提交，便于 review
5. 更新相关文档（如架构变化）
6. 提交 PR 并说明重构带来的改善

## Review 期望

PR 提交后，维护者会检查：

1. 代码质量和风格
2. 测试覆盖和通过情况
3. 文档同步情况
4. 向后兼容性
5. 安全风险

请耐心等待 review 反馈，并及时回应评论和问题。

## 行为准则

- 尊重他人的贡献和意见
- 提供建设性的反馈
- 接受不同的实现方式
- 优先考虑项目整体利益
- 保持友好和专业的态度
