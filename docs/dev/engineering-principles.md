# 工程协作原则

本文从全局协作规范中挑选适合本插件的工程约束。它不是通用个人偏好全集，只记录会直接影响 `astrbot_plugin_get_px` 维护质量的规则。

## 工具与检索

- 能本地处理就先本地处理；确有必要时再联网。
- 先小范围定位，再精读、修改或扩大检索范围。
- 文本检索优先使用 `grep` 或 `rg`。
- 大文件先检索命中位置，再按需分段读取。
- 命令必须显式设置工作目录，不依赖前一次 `cd` 的状态。
- 联网、安装依赖、长任务、破坏性动作或大规模重构前，先说明目的和影响。

## 任务收敛

- 大任务不要直接闷头实现，先澄清目标、边界、影响范围和验收标准。
- 单次改动尽量围绕一个目的；不要把 unrelated 重构塞进修复提交。
- 行为边界不清楚时，优先写计划或列出假设，再开始改代码。
- 使用 `Progress/` 目录记录任务进度、遇到的问题和重要决策。

## 代码组织

- 一个文件只承载单一职责或紧密相关职责。
- 文件开始变大、变杂、难导航时，应优先拆分。
- 优先沿用现有模块、命名和 helper，不为了局部问题发明新风格。
- 中文注释用于解释关键意图、不直观逻辑、约束条件和边界情况；不要写纯噪音注释。
- 入口层（`main.py`）只负责装配和路由，复杂业务逻辑放在领域模块（`checkin/`、`pixiv/`）。

## 限制与保护逻辑

- 不要为了"看起来更稳"而新增无依据的硬编码限制、截断、固定超时、重试上限、静默回退或隐藏兜底。
- 新增限制必须至少满足以下条件之一：
  - 产品、README 或现有文档明确要求
  - 平台、接口或运行环境存在客观限制
  - 沿用项目既有同类约束
  - 有测试或日志证据证明不加会稳定故障
- 新增超时、长度、条数、重试、截断、降级或回退逻辑时，要在代码或文档中说明触发条件、目的和影响。
- 不得让合法内容被静默截断，也不得把真实失败伪装成成功。

## 错误处理

- 错误处理目标是暴露真实问题并方便排查。
- 不要 broad `try/except` 后直接吞掉错误。
- 不要返回空结果冒充成功。
- 日志应尽量区分用户配置缺失、API 不可用、下载失败、过滤拦截和数据库错误。
- 降级路径必须尽量保持可观测，不能偷偷改变成功语义。
- 关键操作（下载、签到、购买）的日志应包含足够上下文（用户、群组、作品、原因）。
- 日志正文统一使用“中文事件描述 + `snake_case=value` 字段”；预期内的跳过与限流使用 `debug`，自动回退与重试使用 `info`，影响功能的异常使用 `warning`，最终失败使用 `error`。

## 验证

- 代码任务完成时默认检查：测试是否补齐、回归是否执行、文档是否需要更新。
- 发图、签到、下载器或前端改动不能只看代码，至少做语法检查和相关路径的最小手工验证计划。
- 配置改动必须同步更新 README、配置文档和相关测试。
- 数据库 schema 改动必须提供迁移逻辑和回滚方案。

## 依赖管理

- 优先使用标准库和已有依赖。
- 添加新依赖前必须说明：
  - 为什么需要这个依赖
  - 考虑了哪些替代方案
  - 依赖的大小和维护状态
- 不要引入不必要的大型依赖。
- 依赖版本应明确指定，避免意外升级。

## 安全边界

- 用户上传的文件路径必须经过安全检查，避免路径穿越。
- 不要在日志中输出完整用户 ID、token 或敏感配置。
- 数据库查询使用参数化，不要拼接 SQL 字符串。
- 外部 API 返回的数据必须验证和规范化。
- 图片下载有大小限制，防止恶意大文件。

## 性能考虑

- 数据库查询尽量使用索引。
- 避免 N+1 查询问题。
- 大量数据处理考虑分页或批处理。
- 图片下载和 T2I 渲染是慢操作，不要在关键路径阻塞。
- 缓存合理使用（签到卡片、节假日数据），避免重复计算。

## 测试原则

- 业务测试围绕值得长期维护的功能、安全和数据边界，优先复用已有领域场景。
- 短期诊断、历史修复过程和文案快照不进入长期测试集；不以用例数量或覆盖率为目标堆叠测试。
- Mock 对象签名必须与实际对象匹配。
- 测试使用临时目录和临时数据库，不污染真实数据。
- 异步测试必须标记 `@pytest.mark.asyncio`。

## 文档原则

- 文档不是可选收尾，是改动的一部分。
- 代码改动导致现有说明失真时，必须在同一 patch 中更新相关文档。
- 文档应描述"是什么"和"为什么"，不要只重复代码。
- 配置字段、命令行为、数据结构变化时，文档必须同步更新。

## 进度记录原则

- 开发任务使用 `Progress/` 目录记录进度。
- 记录内容包括：任务需求、实现清单、当前状态、改动文件、遇到的问题、重要决策。
- 进度文件按日期命名：`Progress/YYYY-MM-DD.md`。
- 同一天有多个任务时使用序号：`Progress/YYYY-MM-DD-01.md`。
- 进度记录保持简洁和事实性，不夸大或隐瞒问题。
